# DSSI Core A 開発記録｜内容変更相関

## 実地ログから見つかった問題

Sprint 3の通信観測は、localhost、ChatGPT上で次まで動作した。

- fetch/XHR系のGET・POST
- Beacon/Ping系のPOST
- 同一オリジン判定
- hostとportの縮約保存
- request body未要求
- 通常ログとチップへの表示

一方、実地ログは二つの概念混同を示した。

### 1. フォーカスと内容変更の混同

フォーカス直後には、ページ固有のGET、POST、Beacon等が複数発生し得る。フォーカスは入力面への接触であり、内容変更ではない。これを通信相関の起点にすると、ページの定常通信を「入力操作に近接した通信」として大量に拾う。

したがってフォーカスは、通常ログと通信相関から外し、その場の判断喚起用チップだけに戻した。

### 2. 活動ログの重複抑制と相関パルス更新の結合

同じ入力面で最初のキー入力を記録した後、活動ログの重複抑制が働くと、通信相関用パルスも更新されなくなっていた。

このため、2.5秒窓は定数上は正しくても、二文字目以降の通常入力によって時計が更新されないケースがあった。日本語IME確定など別経路で新しい入力記録が成立したときだけ通信相関が通りやすく見える現象につながった。

修正後は、信頼済み内容変更ごとに相関パルスを先に更新し、その後で活動ログの重複抑制を適用する。

## 時刻の所属境界

Sprint 3ではService Workerがパルスを受け取った時点で時刻を付けていた。v0.4.1ではContent Scriptが内容変更を観測した時点で`observedAt`を付ける。

```text
内容変更を観測
  ↓ observedAtを付与
runtime message
  ↓
Service Workerで一時保持
  ↓
通信時刻との差を判定
```

これにより「Service Worker受信から2.5秒」ではなく、「DSSIが内容変更を観測してから2.5秒」に近づけた。

ただし、通信通知がruntime messageより先にService Workerへ到達した場合に後から再照合する待機キューは、今回実装していない。

## Cookieヘッダー名検出

利用者との検討から、Cookieを「認証通信」と推定するのではなく、Cookieヘッダー名の検出事実だけを扱うことにした。

採用状態:

- 検出
- 未検出
- 未観測
- 判定不能

「未検出」は不存在を意味しない。

`onBeforeSendHeaders`と`requestHeaders`、`extraHeaders`を使用するため、Chromeのコールバックオブジェクトにはヘッダー値が含まれる可能性がある。したがって「値を取得しない」という強すぎる説明は避け、次を実装保証とする。

> DSSIの検出処理はヘッダー値を参照せず、値をメッセージ、型、記録、storage、UI、consoleへ移さない。

値getterへ触れた場合に例外を投げる単体テストを置き、検出関数が`name`だけを読むことを確認した。

## ページ観測開始との時間関係

ページ読み込み直後の通信は、認証、初期化、状態復元、分析等の可能性がある。しかし、method、host、resource type、Cookie検出だけから用途を確定できない。

そこで用途名を付けず、DSSI自身のページ観測開始から、

- 5秒以内
- 5秒超
- 不明

という時間関係だけを保持する。

これは通信の意味分類ではなく、後からログを読むための中立的な座標である。

## フォーカス表示方針

```text
Level 1
  フォーカス表示なし

Level 2
  パスワード、決済、個人情報のみチップ表示

Level 3
  入力面全般でチップ表示
```

いずれも通常ログへ保存せず、通信相関には使用しない。

## 新しい意味上の正本

新規通信記録は次を用いる。

```text
network_activity_after_content_edit
recent_content_edit
schemaVersion 8
```

旧Sprint 3記録は、旧形式として引き続き表示できる。

## 次の検討

- runtime messageとnetwork eventの到着順逆転を短い保留窓で再照合するか
- Cookieヘッダー名検出が公開版の権限負担に見合うか
- `extraHeaders`の性能影響を実地測定するか
- 通信群を個別ログではなく短時間バーストとして提示するか
- 一般button操作と通信相関を別軸で導入するか
