# DSSI Core A Architectural Design Principles

## DSSI Core A アーキテクチャ設計原則

## 位置づけ

本書は、DSSI Core A がなぜ現在のような機能分離と統合構造を採用しているのかを説明する設計思想文書である。

ファイル責務表が「どのファイルが何を担当するか」を示すのに対し、本書は「なぜ、その責務を分ける必要があるのか」を扱う。

DSSI Core A の構造は、単なる保守性のためのソフトウェア分割ではない。境界で起きた事実を観測し、その証拠強度と観測限界を評価し、意味を複数の軸へ分解し、内容を保存しない形へ縮約し、断定強度を超えない表現で利用者へ返すための認識構造である。

## 1. 基本モデル

DSSI Core A の処理は、最小限には次の三段階として理解できる。

```text
1. 検出する
   何が起きたか、どこまで観測できたか

2. 同定・分類する
   観測結果を、どの概念として扱うか

3. 表示する
   利用者へ、どの強さ・表現で返すか
```

ただし、実装上および認識論上は、次の五段階として捉える方が正確である。

```text
1. 接触を検出する
   DOMイベントや構造変化を観測する

2. 観測可能性を評価する
   trustedか、相関できたか、何が見えていないかを確認する

3. 意味軸へ分解する
   入力面、操作証拠、観測範囲、送信関連づけ等へ分類する

4. 記録可能な形へ縮約する
   内容や不要な識別情報を捨て、ObservationRecordへ変換する

5. 利用者へ返す
   証拠強度を超えない文言とUIで提示する
```

DSSI Core A に固有なのは、特に第二段階と第四段階である。

一般的なアプリケーションは、検出、分類、表示で終わることが多い。DSSIはそれに加えて、「どこまで観測できたか」と「何を捨てて記録するか」を独立した工程として持つ。

## 2. 関心の分離

DSSI Core A は、異なる種類の判断を一つの処理へ混ぜない。

たとえば、単一の関数が次のすべてを担当するとする。

```text
DOMイベントを受け取る
入力欄を分類する
ログ文言を決める
保存する
チップを表示する
```

この構造では、表示文言を変更しただけで観測処理へ影響し、分類規則を変更しただけで保存形式へ影響し得る。また、どの段階で意味が付与されたのかが不明になる。

DSSI Core A では、概ね次のように責務を分離する。

```text
Observer
  ブラウザイベントを観測する

Classifier
  入力面や操作を分類する

Factory
  ObservationRecordを組み立てる

Service Worker
  タブ・フレーム等の文脈を補完する

Storage
  記録を保存する

Presentation
  観測結果を表示用の表現へ変換する

UI
  表、Popup、チップとして提示する
```

この分離は、保守性だけでなく認識上の責任分離である。

> 観測、推定、分類、保存、表示を混ぜると、システム自身が何を知っているのか分からなくなる。

## 3. 単一責任原則

各モジュールは、原則として一種類の変更理由を持つ。

例として、入力面観測を担当するファイルが変更される理由は、ブラウザ上で入力面をどう観測するかが変わった場合である。

一方、表示変換を担当するファイルが変更される理由は、観測結果をどう表現するかが変わった場合である。

この二つは分離されなければならない。

たとえば、DOM上の `submit` イベントしか観測していないのに、UIが「メッセージを送信しました」と表示すれば、表示が観測事実を越えてしまう。

DSSI Core A では、次のように分けて点検できる。

```text
観測値:
  submitイベント

表示:
  フォーム送信イベントを観測
```

観測層と表示層の分離により、表現が証拠強度を超えていないかを独立して監査できる。

## 4. レイヤードアーキテクチャ

DSSI Core A は、概ね次の層構造を持つ。

```text
ブラウザ／DOM層
  ↓
観測層
  ↓
ドメインモデル層
  ↓
保存層
  ↓
表示層
```

UIは生の `PasteEvent` や `SubmitEvent` を直接扱わない。UIが扱うのは、正規化されたObservationRecordである。

```text
eventType: paste_event_observed
operationEvidence: trusted_direct_event
```

この構造により、将来Chrome以外の環境へ移行する場合でも、観測アダプターだけを差し替え、記録モデルや表示原則を再利用できる可能性が残る。

## 5. イベント駆動設計

DSSI Core A の入口は、ブラウザイベントである。

```text
focusin
keydown
paste
beforeinput
input
click
submit
```

DSSIは状態を直接所有するのではなく、境界で起きた状態変化をイベントとして受け取る。

さらに、単一イベントだけでなくイベント列を扱う。

```text
paste
  ↓ 300ms以内
input
```

この場合、貼り付け操作と入力面への反映を相関できる。

```text
submit要素へのclick
  ↓ 1500ms以内
同一formのsubmit
```

この場合、submit操作面とsubmitイベント成立を相関できる。

単一点だけで意味を断定せず、接触履歴の並びによって証拠強度を高める設計である。

## 6. 処理パイプライン

DSSI Core A の処理は、次のパイプラインとして整理できる。

```text
Raw Event
  生のブラウザイベント

Detection
  対象イベントを検出

Qualification
  trustedか、対象要素かを確認

Correlation
  前後イベントとの関係を確認

Classification
  入力面・操作証拠・観測範囲を分類

Normalization
  ObservationRecordへ統一

Enrichment
  タブ・フレーム情報を補完

Validation
  保存禁止情報が含まれていないか検査

Persistence
  session storageへ保存

Presentation
  表示文言へ変換

Interaction
  Popup・ログ表・チップで提示
```

このパイプラインにより、どの段階で不確実性が発生したかを示せる。

```text
イベントは検出した
対象入力面も確認した
しかし入力経路との相関に失敗した
```

この場合、全体を失敗として捨てるのではなく、「入力経路不明」として記録できる。

## 7. 検出不能を結果として扱う

通常のソフトウェアでは、検出できなかった場合、`null`、`undefined`、例外、無記録などで処理されることが多い。

DSSIでは、検出不能や根拠不足自体が重要な情報である。

```text
入力経路不明
分類根拠なし
submitイベント単独観測
通信成立は未観測
拒否経路を検出できず
```

DSSIが扱う状態は、成功と失敗の二値ではない。

```text
観測できた
部分的に観測できた
推定しかできない
観測できなかった
観測対象外である
```

これは一般的なResult型や明示的エラー状態に近いが、DSSIではエラー処理ではなく、認識限界のモデル化として用いる。

> 分からなかったことを、なかったことにしない。

## 8. ドメインモデル

ObservationRecordは、単なるログ行ではない。DSSIが境界事象をどの軸で分解するかを示すドメインモデルである。

主な軸は次のとおりである。

```text
何が起きたか
  observation fact

どのような証拠か
  operation evidence

何を対象として分類したか
  input surface classification

どこまで観測できたか
  observation scope

送信との関係は何か
  submission association

どのフレームで起きたか
  frame context
```

この分け方は一般的な唯一の正解ではない。DSSIの目的に応じて、世界をこの軸で切り分けている。

DSSIにおける「貼り付け」「送信」「自由記述」「操作証拠」「観測範囲」は、日常語のままではなく、実装上の定義を持つユビキタス言語である。

## 9. 外部技術とドメイン意味の分離

DSSI Core A は、Chrome APIやDOM仕様の語彙をそのまま社会的意味へ昇格させない。

Chromeが `submit` イベントを提供するからといって、DSSIは次のようには定義しない。

```text
submit = 通信成立
```

DSSIのドメインモデルでは、次のように分離する。

```text
submit
  DOM上のフォーム送信イベント

通信成立
  未観測
```

外部APIの都合を、利用者へ返す意味へ直接変換しない。これは、ヘキサゴナルアーキテクチャ的な中心と外部アダプターの分離に近い。

## 10. 観測可能性の二層化

一般的なObservabilityは、ログ、メトリクス、トレースを通じて開発者がシステム内部を理解するために用いられる。

DSSIは、この構造を利用者側へ反転する。

```text
一般的なObservability:
  開発者がシステム内部を理解する

DSSI:
  利用者が自分とデジタルシステムの境界で何が起きたか理解する
```

そのため、通常ログと診断ログを分離する。

```text
通常ログ
  利用者の判断に必要な記録

診断ログ
  DSSI自身の動作確認に必要な記録
```

観測対象の出来事と、観測装置自身の状態を混同しないための分離である。

## 11. データ最小化と保存境界

DSSIでは、観測に必要な情報、保存してよい情報、表示してよい情報を分ける。

```text
観測に必要な情報
  ≠
保存してよい情報
  ≠
表示してよい情報
```

たとえば、入力面分類には `placeholder`、`label`、`name`、`id` 等が役立つ場合がある。しかし、そのまま保存すると利用者の入力文脈を漏らす危険がある。

したがって、次の原則を採る。

```text
分類時には参照する場合がある
保存時には捨てる
表示時には安全な構造情報だけを使う
```

これは、プライバシー・バイ・デザイン、データ最小化、最小権限の原則に対応する。

## 12. DSSI固有の規範

### 12.1 観測と意味を分離する

イベントが起きたことと、そのイベントが何を意味するかを同一視しない。

### 12.2 意味と断定強度を分離する

フォームに関連する操作だったことと、利用者が社会的意味で送信を意図したことを同一視しない。

### 12.3 観測不能を明示する

分からないことを空欄にせず、記録可能な状態として持つ。

### 12.4 システム内部の都合を利用者の意味にしない

DOM仕様やChrome API上の名称を、そのまま利用者向け意味へ変換しない。

### 12.5 表示を証拠強度以上にしない

観測できた範囲を超える文言を表示しない。

### 12.6 内容ではなく境界を観測する

本文を読むのではなく、入力面への接触、貼り付け、送信候補、宣言上の送信先などの境界事象を扱う。

### 12.7 観測装置自身の限界もモデル化する

DSSIは対象だけを観測するのではなく、自らが何を観測できず、どこから推定へ移るかも記録する。

## 13. 機能理解からソース理解へ

DSSI Core A を理解する際は、次の順序が有効である。

```text
目的
↓
機能
↓
責務
↓
構造
↓
実装
```

その後、逆方向へ照合する。

```text
実装
↓
構造
↓
機能が本当に成立しているか
↓
目的に反していないか
```

機能を先に把握しておくことで、ソースコードは「何をしているかを発見する対象」ではなく、「既知の機能が、どの技術で成立しているかを確認する対象」になる。

## 14. 中核定義

DSSI Core A の規範的モデルは、次の一文に要約できる。

> DSSIは、境界接触を検出し、その証拠強度と観測限界を評価し、意味を複数軸へ分解し、内容を保存せずに記録可能な形へ縮約し、断定強度を超えない表現で利用者へ返す。

この原則は、今後DSSIが入力境界、送信境界、同意境界、証拠形成へ拡張される場合にも維持されるべきである。

## 15. 今後の照合項目

今後の実装変更では、少なくとも次を確認する。

```text
新機能はどの境界を観測するか
観測事実と推定は分離されているか
観測不能状態は明示されるか
保存禁止情報が混入していないか
外部APIの語彙を意味として過剰利用していないか
表示文言は証拠強度を超えていないか
通常ログと診断ログが混ざっていないか
テストはどの設計原則を保証しているか
```
