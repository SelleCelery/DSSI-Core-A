# AI Top-Down Architectural Generation in DSSI

## DSSIにおけるAIトップダウン設計生成

## 位置づけ

本書は、DSSI Core A の設計過程を、AIが抽象的な規範から機能、責務、実装構造を生成し、実地ログから返された事実によって概念モデルを修正した事例として記述する研究ノートである。

DSSI Core A は製品試作であると同時に、抽象的な規範をAIとの協働によってソフトウェア構造へ落とし、その実装から返る事実によって規範の分解自体を再構成する実験でもある。

本書は、AIが人間の設計者を代替したと主張するものではない。人間、AI、実地環境がどのように役割を分担し、設計履歴を形成したかを整理する。

## 1. 問題設定

今回の開発では、AIは単なるコード生成器としてではなく、次の変換を担った。

```text
抽象的な目的
「利用者の判断場を壊さず、デジタル境界を観測可能にする」

↓ 制約へ変換

入力本文を読まない
観測と推定を分ける
観測不能を明示する
表示が証拠強度を超えない
Chrome拡張として実装可能である

↓ 機能へ分解

入力面検出
操作イベント検出
証拠相関
分類
記録
保存
表示

↓ 責務へ分解

Observer
Classifier
Factory
Service Worker
Storage
Presentation
UI

↓ 技術へ対応

DOM Events
TypeScript types
chrome.runtime messaging
chrome.storage.session
HTML / CSS
```

これは、上位規範を中間的な設計制約へ翻訳し、さらに実装単位まで降ろすトップダウン変換である。

## 2. トップダウン設計の内容

AIが利用したと考えられる一般的な設計規範には、次がある。

```text
関心の分離
単一責任原則
レイヤードアーキテクチャ
イベント駆動設計
ドメインモデル
プライバシー・バイ・デザイン
明示的な不確実性表現
テスト可能性の確保
```

ただし、既存パターンを並べただけではDSSIにはならない。

DSSIでは、上位の価値序列がパターン選択を制約した。

一般的な入力解析ツールであれば、精度向上のため入力内容を読む設計も合理的である。しかしDSSIでは、本文非取得が上位原則にあるため、分類精度を一部犠牲にしてでも内容非保存を優先した。

したがって生成されたのは、一般的に最も高性能な実装ではなく、DSSIの規範に従った実装である。

## 3. AIが設計できた理由の分解

AIがトップダウン設計を行ったように見える場合、少なくとも三つの要因を区別する必要がある。

### 3.1 既存パターンの再構成

AIは、多数のソフトウェア設計事例から、要求に合うパターンを再構成できる。

DSSI Core A の責務分離も、完全に新しいソフトウェア原理ではない。既存の設計原則を、DSSI固有の規範へ合わせて組み替えたものである。

### 3.2 会話履歴からの制約抽出

開発者が繰り返し示した次の要請が、設計制約として抽出された。

```text
判断を代行しない
境界を観測する
内容を取得しない
観測強度を誇張しない
履歴を残す
観測できないことも明示する
```

AIはこれらを、単なる説明文ではなく、型、モジュール責務、ログ項目、表示文言、テスト条件へ変換した。

### 3.3 実地観測による概念モデル修正

DSSIの設計は最初から完成していたわけではない。

初期には、自由記述入力面が一般分類であることと、イベント観測の確実性が混同されていた。

実地ログから、次の混同が発見された。

```text
自由記述だから分類が一般的である
  ≠
イベント自体が不確実である
```

その結果、次の三軸が分離された。

```text
操作証拠
入力面分類根拠
境界観測範囲
```

ここでは、AIは実装から返った観測結果を受けて、上位概念の分解方法自体を修正している。

## 4. 生成ではなく循環

DSSI Core A の設計履歴は、単純な一方向生成ではない。

```text
要求
↓
暫定設計
↓
実装
↓
実地ログ
↓
概念上の混同を発見
↓
軸を再分離
↓
再実装
```

したがって研究対象は、AIが最初から正しいアーキテクチャを生成できるかではない。

より重要なのは、次である。

> AIは、実装から返ってきた観測結果を受けて、上位概念の分解方法を改訂できるか。

DSSIでは、貼り付け検出、フォーム送信、iframeノイズ、通常ログと診断ログの分離などにおいて、この循環が繰り返された。

## 5. 人間・AI・実地環境の役割

今回の設計は、AI単独の成果ではない。

```text
人間の設計者
  目的と規範を提示する
  実地操作を行う
  ログの意味的不自然さを発見する
  許容・不許容を判断する
  社会的・倫理的な意味を評価する

AI
  規範を機能へ分解する
  機能をコード構造へ変換する
  修正案を実装する
  テストと文書を生成する
  構造を言語化する

実地環境
  実際のブラウザ挙動を返す
  机上設計の誤りを露出させる
  実在サイト固有のノイズや例外を示す
```

この三者は、上下関係ではなく循環関係にある。

```text
規範
→ 実装
→ 接触
→ 履歴
→ 返り
→ 再照合
```

DSSIの開発過程自体が、DSSIの扱う境界接触と履歴再構成の形式を持つ。

## 6. 機能理解と構造理解

ソースコードを先に読む場合、理解は次のように進む。

```text
コード断片
↓
局所処理
↓
機能を推測
↓
システム全体での意味を推測
```

一方、機能を先に理解してからソースを読む場合は、次のようになる。

```text
システム上の機能
↓
責務の分離
↓
対応するファイル
↓
技術的な実現方法
```

後者では、TypeScriptやChrome APIの一部が分からなくても、各処理を次のように位置づけられる。

```text
この部分は検出手段の実装である
この部分は意味分類である
この部分は観測結果の保存形への変換である
この部分は表示上の翻訳である
```

AIによるトップダウン設計は、人間に対しても、先に機能と責務を提示し、その後に技術実装を読む経路を作れる。

これは、AI協働開発における理解支援の重要な可能性である。

## 7. 設計所有権の問題

AIが大量のコードを短時間で生成すると、次の逆転が起こり得る。

```text
コード量
  >
仕様理解
  >
実装者本人の検証能力
```

この状態では、動作している間は問題が見えにくいが、次の危険が生じる。

```text
不具合が仕様違反か実装ミスか判断できない
修正の影響範囲を評価できない
セキュリティ上の危険を自分で発見できない
外部開発者へ設計意図を渡せない
コードが規範と逆方向へ進んでも止めにくい
```

必要なのは、すべてのコードを自力で書けることではなく、所有可能な理解である。

最低限、設計者は次を説明できる必要がある。

```text
このファイルは何を担当するか
どのイベントを受け取るか
どの情報を読むか
何を保存するか
何を保存しないか
どの根拠で分類するか
どの条件でチップを出すか
観測不能な部分はどこか
テストが何を保証しているか
```

AIが生成したアーキテクチャを人間が所有するとは、コード全文を暗記することではなく、目的、機能、責務、境界、検証方法を説明可能にすることである。

## 8. 説明可能性の問題

AIは完成したコードに対して、後からもっともらしい設計思想を付与することもできる。

したがって、説明が本当に実装構造へ反映されているかを照合する必要がある。

DSSI Core A では、設計思想が次の実装要素へ現れている。

```text
型の分離
ファイル責務の分離
ObservationRecordの複数軸
通常ログと診断ログの分離
表示文言の限定
privacy-safe logger
イベント相関窓
未観測・不明状態の明示
```

このため、設計説明は完全な後付けではなく、実装構造から検証可能である。

ただし、今後も次を区別しなければならない。

```text
実装前から保持されていた原則
実装中に生成された中間概念
実地ログによって修正された概念
完成後に説明用として再構成された表現
```

## 9. 研究上の主要論点

### 9.1 規範から実装への翻訳可能性

抽象的な倫理的・認識論的要請を、どこまでソフトウェア責務へ変換できるか。

### 9.2 設計パターンの選択理由

AIが一般的な設計パターンのうち、なぜその組み合わせを選んだか。

### 9.3 意味軸の生成

操作証拠、入力面分類根拠、観測範囲などの軸は、最初から与えられたのか、実地ログとの照合によって生成されたのか。

### 9.4 誤りの型

コード上のバグだけでなく、概念の混同をAIが発見・修正できるか。

### 9.5 設計所有権

AIが構造を生成したとき、人間はどの程度理解すれば、その設計を自身の判断対象として所有できるか。

### 9.6 説明可能性

完成したコードから後付けで説明を作ったのか、説明可能な中間構造を保ちながら実装したのか。

### 9.7 規範の保持

機能追加や精度向上の圧力の中で、内容非取得、断定強度制限、観測不能の明示といった上位規範を保持できるか。

### 9.8 現実からの返り

実在サイトの挙動が、AIの生成した概念モデルをどのように修正するか。

## 10. DSSI開発履歴の研究資料性

DSSIのSprint記録は、単なるCHANGELOGではない。

各Sprintには次が残されている。

```text
初期要求
暫定モデル
実装内容
実地ログ
誤認またはノイズ
概念軸の修正
表示文言の修正
観測限界の追加
```

特に次の変化は、AIトップダウン設計生成の履歴として重要である。

```text
入力面分類とイベント観測確度の分離
貼り付けイベントと貼り付け反映の分離
submit操作面とsubmit成立の分離
トップフレームと埋め込みフレームの分離
通常ログと診断ログの分離
同意ビットと同意成立履歴の分離
```

これらは、単なるコード修正ではなく、世界をどの軸で分解するかの修正である。

## 11. AI協働開発の暫定モデル

DSSIの経験から、AI協働によるトップダウン設計は次のようにモデル化できる。

```text
Human Normative Intent
  人間が目的・禁止・価値序列を提示

AI Architectural Translation
  AIが制約・機能・責務・型へ変換

Executable Prototype
  実行可能な試作へ落とす

Boundary Contact
  実地環境で接触させる

Observed Return
  ログ・誤作動・ノイズ・未観測領域が返る

Joint Re-Collation
  人間とAIが意味軸と実装を再照合する
```

このモデルでは、AIは完成品を一度に生成する存在ではない。

AIは、規範と現実の間に中間構造を生成し、現実から返る結果を受けてその中間構造を再編する役割を持つ。

## 12. 限界

本事例だけから、AI一般がトップダウン設計能力を持つと断定することはできない。

少なくとも次の留保が必要である。

```text
設計品質は人間側の規範提示に依存する
会話履歴が長く、DSSI固有の文脈が豊富である
AIは既存設計パターンを再構成している可能性が高い
実装検証の多くは人間の実地操作へ依存する
セキュリティ・法的保証・認証は外部専門家を必要とする
説明の一部は完成後の再構成である可能性がある
```

したがって、研究上は「AIが自律的に設計した」と単純化せず、どの入力、履歴、規範、実地結果によって設計が形成されたかを追跡する必要がある。

## 13. 暫定結論

DSSI Core A の開発は、次の可能性を示している。

> AIは、抽象的な規範を機能、責務、型、モジュールへトップダウンに翻訳し、実地観測から返された結果によって、その概念分解を修正する協働的設計主体として機能し得る。

ただし、その成立には、人間による目的設定、禁止境界、実地評価、意味判断が必要である。

DSSIの設計は、AIが人間に代わって完成させたものではない。

それは、人間が規範を示し、AIが中間構造を生成し、実地環境が返りを与え、人間とAIが再照合することで形成された履歴的な設計である。
